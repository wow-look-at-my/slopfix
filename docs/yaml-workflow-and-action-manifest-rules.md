# yaml: workflow and action manifest rules

These rules judge the format. The prose rules never run on these files. A file is read when its base name is `action.yml` or `action.yaml`, or when it is YAML under a `workflows` directory. Other YAML with a left-margin `jobs:` or `runs:` key qualifies too.

- `yaml/comment-block`: a run of comment lines past the single-line limit. A blank line neither counts nor ends a run. The repair joins the run into the allowed line and keeps every word.
- `yaml/all-builds-job`: a job named `all-builds`, by key or rendered name. The required gate is a commit status from the required-builds-manager app. A job with that name shadows it. The repair renames the job to `builds` and fixes each `needs` entry.
- `yaml/test-in-workflow`: a test inside a `run:` script. That is an assertion with a nonzero exit, a function whose name says it asserts, or a redirect to a test file. It is a warning. A line of a `run:` script is shell, and slopfix does not delete it. The repair moves the whole script into a file under `.github/scripts`, named for the workflow, the job and the step, and the step runs that file with its own shell. Each `${{ }}` expression becomes an argument of the command, and the script reads the argument where the expression stood. A caller that writes the workflow alone, such as a hook, gets no change.
- `yaml/neutered-gate`: a gate step under `continue-on-error`. A step allowed to fail is not a gate. The repair deletes that line, found by parser positions.
- `yaml/env-indirection`: a step `env:` entry with no job to do. Its value is a single `${{ }}` expression that the script reads only as `$NAME` or `${NAME}`. Or the script sets the variable before it reads it. Only an expression whose value holds no shell text moves into `run:`: a `runner` fact, a `github` id, hash or restricted name. This is a `strategy` number, or an input that is a `boolean` or a `number` on every trigger. Any other expression stays in `env:` and is not reported, because its quotes end a quoted script word. An outside party can write it. That is a step output, a matrix value, a `github.event` field, `github.head_ref`, `github.ref_name`, a secret, and every input of a composite action. A runner variable such as `$RUNNER_TEMP` is also reported, because a context names it. A container job and a composite action keep the variable, because the context names the host path there. The repair writes the expression into the script, deletes the entry, and deletes an `env:` key with nothing left under it.
- `yaml/push-tags`: a `push` trigger with no `branches`, `branches-ignore`, `tags` or `tags-ignore` filter. Every tag push then starts the workflow again. The repair writes `branches: ['**']` under `push:`. A shape no line edit reaches, such as `push: {}`, gets its whole `on:` value written again in block style.
- `yaml/org-action-ref`: a `uses:` of a `wow-look-at-my` action or reusable workflow at a ref other than `master`. A `wow-look-at-my/actions` orphan tag `<directory>#latest` is published from master, and passes. A feature branch breaks the moment it merges, and an agent that pins one to dodge a check has bypassed the org's tooling. The repair writes `@master`. A numbered orphan tag becomes `#latest`, and a bare `actions@<directory>` becomes `<directory>#latest`.
- `yaml/concurrency`: a workflow whose top-level `concurrency:` is not the org's block. Off master the group names the repository, the workflow and the ref, and `cancel-in-progress` is true. A push then cancels the run before it. On master the group holds the run ID, so every run completes. The workflow name is in the group because a group spans every workflow in the repository. The repair writes the block after `on:`, or writes the old block again. A reusable workflow is skipped, because it runs in the caller's context, and the same group then deadlocks. A job-level `concurrency:` stays the author's.

- `yaml/private-runner`: a job of a `wow-look-at-my` repository whose `runs-on` ignores the repository's visibility. That is a GitHub-hosted Linux label (`ubuntu-latest` or `ubuntu-<version>`), or an expression that falls back to one with no visibility test, such as `${{ vars.CI_RUNNER || 'ubuntu-latest' }}`. GitHub bills each minute a private repository spends on its runners, and the org owns runners. The repair writes `${{ github.event.repository.visibility == 'public' && '<label>' || vars.CI_RUNNER || '<label>' }}`, and `vars.CI_RUNNER_DIND` in place of `vars.CI_RUNNER` for a job that runs docker. A job runs docker when it has a `services` or `container` key, a `uses:` that names docker or buildx, a `docker://` image, a container action, or a script line that runs the docker client. An old expression that names `vars.CI_RUNNER_DIND` keeps it. The run reads the visibility from its own event payload. The rule therefore asks nothing about the visibility at lint time, and a repository that changes visibility needs no new commit. An event whose payload holds no repository reads as not public, and goes to the org runners. The repository is the one `origin` names, as [fork-scope.md](fork-scope.md) says. `SelfHostExempt` in `workflow/runner.go` names each repository the self-hosted runner fleet depends on, so a fleet outage cannot block its own fix. A macOS, Windows or arm label, a list, and any other expression are not read, except one matrix value.

  A `runs-on` that is exactly `${{ matrix.<key> }}` is read when the job's `strategy.matrix` writes that key out: a list under the key, `include:` entries that set it, or both. The rule reports it when one of those values is a hosted Linux label. The repair writes `${{ (github.event.repository.visibility == 'public' || !contains(fromJSON('["ubuntu-22.04","ubuntu-24.04"]'), matrix.os)) && matrix.os || vars.CI_RUNNER || matrix.os }}`. The JSON list holds exactly the hosted Linux values of the matrix. Every other value, such as a macOS, Windows, arm or self-hosted label, keeps its runner. A public repository keeps every value. A docker job gets `vars.CI_RUNNER_DIND`. A matrix that the file does not write out, such as `fromJSON` of an output, is not read.

  A container action is one whose `action.yml` or `action.yaml` says `runs: using: docker` at the ref the step names. The rule reads that file through the GitHub contents API for each action outside `actions/*` and `wow-look-at-my/*`, and keeps each answer in `slopfix-actions.json`. That `slopfix-actions.json` is in the git common directory. A walk thus asks once for each action at each ref. When the file cannot be read, the job goes to `vars.CI_RUNNER_DIND`, which runs both kinds of action. The finding says why.

  No job keeps a GitHub-hosted label. A job that boots a VM or needs the host kernel goes to the org runners too. No comment opts a job out.

The all-builds wording is the operator's own. It must not be softened. A job that wears the required status's name is a known deception attempt.

Unparseable YAML yields no all-builds finding, because the runner fails on it anyway. A job name that holds an expression is skipped. A matrix suffix and a reusable workflow's path parts are stripped. A segment must then match exactly. A step that only runs a command is not a test. An error annotation alone is a report. Every repair works on whole lines and never reflows.
